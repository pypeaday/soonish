# Proof: agentic validation — `just verify`, worktree bootstrap, PROOF.md manifest

**

## Change

Adds the validation system from nic/notifiq#22: a single `just verify` entry
point (backend lint + tests on an ephemeral Temporal, every `frontend-*` lint +
build), `scripts/agent-worktree.sh` for isolated per-agent worktrees,
`PROOF.md`/`PROOF.example.md` + `scripts/proof` as the manifest convention, a
`.forgejo/workflows/verify.yml` CI job with a PROOF.md gate, and the agent
contract in `AGENTS.md > Verify`.

Backend code change is one line (`# noqa: E402` in `src/api/main.py`) plus a
pinned ruff rule set in `pyproject.toml`; everything else is tooling and docs.

Evidence below was captured in a worktree created by the new script
(`../notifiq-worktrees/dogfood`), i.e. the system was used to prove itself.

## Claims

1. `scripts/agent-worktree.sh` bootstraps an isolated worktree whose `.env`
   points at **local** Temporal with a task-queue unique to the worktree —
   never `ghost:7233`.
2. Port allocation is dynamic, so two concurrent worktrees cannot collide on
   8000/8001/7233.
3. The integration path refuses to run (loudly, non-zero) when the `temporal`
   CLI is missing — it never silently "passes".
4. `just verify` fails non-zero and names the failing step when something is
   broken.
5. `VERIFY_FRONTENDS` scopes the frontend sweep, and a bad value is rejected.
6. The PROOF.md CI gate actually detects a missing/unchanged manifest.
7. `.forgejo/workflows/verify.yml` is valid YAML with the expected jobs.
8. `scripts/proof` records real command output and can re-verify it.
9. Baseline: `just verify` is green on this branch (backend + all 12 frontends).

### Claim 8: recorded evidence is re-verifiable

`scripts/proof` wraps `uvx showboat`. Demonstrated on a throwaway document so
this block does not recurse into PROOF.md itself: a recorded block re-verifies
clean, and tampering with the recorded output is detected.

```bash
export PROOF_FILE=/tmp/proof-demo.md; rm -f $PROOF_FILE
./scripts/proof init "demo" >/dev/null
./scripts/proof exec bash "echo \$((2 + 2))" >/dev/null
echo "--- the recorded block:"; sed -n "/\`\`\`bash/,\$p" $PROOF_FILE
echo "--- verify unmodified:"; ./scripts/proof verify; echo "rc=$?"
echo "--- now hand-edit the recorded OUTPUT from 4 to 5 and re-verify:"
sed -i "s/^4$/5/" $PROOF_FILE
./scripts/proof verify; echo "rc=$?"
rm -f $PROOF_FILE
```

````output
--- the recorded block:
```bash
echo $((2 + 2))
```

```output
4
```
--- verify unmodified:
rc=0
--- now hand-edit the recorded OUTPUT from 4 to 5 and re-verify:
block 1:
  expected: 5
  actual:   4
rc=1
````

## Not proven

- **Backend integration suite end-to-end.** This environment has no `temporal`
  CLI (Claim 3 proves the refusal path). The happy path of
  `backend/justfile test-full` — ephemeral `temporal server start-dev` on a free
  port, worker on the per-run task queue, the 68 `integration`-marked tests
  passing — has never executed. Specifically unverified: the
  `temporal server start-dev --port N --headless` invocation and the
  `temporal operator cluster health --address` readiness probe. Needs one run by
  a human (or CI) with the CLI installed.
- **CI runner behaviour.** `.forgejo/workflows/verify.yml` is verified as YAML
  with the expected jobs/steps (Claim 7) and its gate step is the same script
  proven in Claim 6, but the tool-bootstrap steps (uv / just / temporal CLI /
  `actions/setup-node`) have not run on an actual `docker` runner. If the
  temporal install step fails there, `just verify` reports integration as
  `NOT RUN` rather than failing the build — watch the first run.
- **Cold npm cache.** `npm ci` here hit a warm local cache; CI timing is
  unknown.
- **Frontend eslint.** Deliberately advisory: ~75 pre-existing findings across
  9 apps remain unfixed, so lint failures do not fail the build by default
  (`VERIFY_LINT_STRICT=1` makes them fail). `npm run build` is the hard gate.

# Round 2 — review additions (service lane, per-PR manifests, scripts audit)

## Change (round 2)

Three additions on top of the original agentic-validation commit:

1. **Service lane**: `test-full` now boots a fake SMTP sink
   (`backend/scripts/sink_smtp.py`, aiosmtpd, STARTTLS + login — the exact
   Apprise `mailtos://` path production uses) and exports `SMTP_*` +
   `MAIL_SINK_FILE` before the API starts. New `service`-marked tests in
   `tests/test_service_delivery.py` assert against real captured SMTP
   envelopes: verification email, password reset, email channel, SMS to a
   carrier gateway (`<number>@vzwpix.com` etc.), and tag fan-out. Two real
   bugs were found and fixed making this work: `test-full`'s `*PYTEST_ARGS`
   was never forwarded to pytest, and `convert_email_to_apprise` /
   `convert_sms_to_apprise` silently ignored `SMTP_PORT` (channel
   notifications would always go to port 587 — verified by the sink).
2. **Per-PR proof manifests**: `PROOF.md` moved to `proof/<branch-slug>.md`
   so open PRs stop conflicting on one file. `scripts/proof` resolves the
   slug from the branch name, `just proof-init` creates it, and
   `check-proof.sh` (the CI gate) now requires a *new* `proof/*.md` vs base
   with no unfilled placeholders. The repo root keeps **no pointer file** —
   the convention is documented in AGENTS.md and manifests live only under
   `proof/`.
3. **Scripts audit**: `backend/scripts/README.md` now categorizes all
   `test_*.py` scripts. One was promoted (`test_auth_tokens.py` →
   `tests/test_auth_workflows.py::TestApiTokens`); the rest are manual-only
   or stale (every HTTP-driving script predates the `/api/v1` prefix).

## Not proven (round 2)

- **The integration lane now runs — and 23 pre-existing tests fail.** This is
  the first environment with a `temporal` CLI, so `just verify` exercised the
  full suite for the first time and surfaced drift that predates this branch:
  - `test_adhd_reminders.py` (10) + `test_workflow_notifications.py` (4):
    `Activity function create_next_occurrence ... is not registered on this
    worker` — the tests' mock `Worker(activities=[...])` lists were never
    updated when `src/workflows/event.py` started calling that activity.
  - `test_auto_subscriptions.py` (5 + cascading KeyErrors): the tests register
    users inline and never complete email verification, so
    `require_verified_user` endpoints return 403 where they expect 201.
  - `test_auth_workflows.py::test_register_duplicate_email_rejected`:
    expects 409, API returns 400.
  - `test_event_workflows.py` (2): expects 422, API returns 500.
  None of these touch code changed on this branch (nothing in the diff
  touches registration semantics, verification requirements, workflows, or
  event validation). They are listed here instead of being silently fixed —
  fixing them is a separate PR with product-behaviour decisions (e.g. 400 vs
  409, 500 vs 422).
- **Same-directory concurrent lanes interfere.** Running `just test-services`
  while another `test-full` was in flight in the same checkout produced
  registration 500s; the same lane run solo passes 6/6. Free ports prevent
  port collisions but not resource contention — the intended model is one
  lane per worktree (`scripts/agent-worktree.sh`), which remains unproven for
  truly parallel runs on this machine.
- **`just verify` is RED on this branch** — only on `backend tests
  (integration)`, for the 23 pre-existing failures above. Everything else is
  green (see baseline below). CI will fail the same way until the pre-existing
  suite is repaired.
